# Corex: Pushing the Boundaries of Complex Reasoning through Multi-Model Collaboration

## One line
Corex has five LLM agents solve a reasoning question in one of three collaboration modes (Discuss, Review, Retrieve), and with five agents it matches or beats self-consistency voting over ten chains at a fraction of the tokens.

## Method
The problem: a single LLM reasoning alone makes three kinds of error. It misreads the question, makes arithmetic slips, or writes buggy code. Self-correction by the same model does not fix these reliably, and the paper cites work showing that. Majority voting over many sampled chains fixes some of them, but a correct minority answer gets outvoted, cost grows with the number of samples, and accuracy saturates. Voting also looks only at the final answer, not at whether the reasoning supports it.

Corex replaces the extra samples with a few agents that check each other, in three modes:

- **Discuss.** Agents are split into a Blue and a Green team, with one agent held back as judge. Each team revises its chains over up to T rounds. If the teams agree, the discussion stops. If they disagree, the judge reads every round and decides. The authors chose team discussion over a debate to a single common answer for three reasons. Context length cannot hold a full debate. Models can reach an erroneous consensus. A strong model can "monopolize" the exchange. The reasons are given as motivation, and the paper does not test them directly.
- **Review.** One primary agent writes a chain of thought and, optionally, Python code. The other agents review it one after another. Each reviewer sees its predecessor's revised solution and the feedback, and edits it. The last version is accepted, and code is run by an interpreter. This is a critique loop across different models, not one model critiquing itself.
- **Retrieve.** Several agents solve the question independently. A retriever agent scores each chain-and-answer pair from 0 to 1 for how faithful the explanation is to its answer, and the top-scored pair is the final answer. The retriever uses no reference and no token probabilities, so it works with closed APIs.

Nothing is trained. The agents are the same API models under different roles, and the harness fixes the order, the round cap and the final-answer rule.

## Evaluated on
Mainly GPT-3.5-Turbo on 18 tasks: arithmetic, commonsense, symbolic and financial table reasoning.
- Beats voting at half the agents: ReviewCode averages 86.7 on seven math sets vs 84.6 for CoT-SC(10) and PAL. Retrieve averages 86.3.
- Code review helps most where the model computes badly: GSM-Hard 63.6 vs 62.1 for PAL alone, and Repeat Copy 96.9 vs 93.8 for PAL and 53.1 for CoT-SC(10).
- Each mode fits a task type. Discuss does best on commonsense (StrategyQA 68.4 vs 67.1 for CoT-SC(10)). Retrieve is best on average for commonsense (77.6 vs 76.5) and for FinQA/ConvFinQA (56.6 vs 54.9).
- Cheaper at matched accuracy: on AddSub the three modes use 5-10% of the tokens of the strong baselines.
- Beats the other multi-model methods, with a small margin. On AddSub, Corex-Retrieve scores 90.9 and Corex-Discuss 89.7, vs 88.6 for debate and 88.0 for Exchange of Thought. Any collaboration beat Self-Refine (shown in a figure, no numbers).
- A judge's strength matters in Discuss, and it matters more as tasks get harder. A retriever's strength matters little, because the candidates cap the result.

## Limitations admitted by the authors
- Open-source models were tested only at small scale (LLaMA-2 7B/13B as primary agent in Review). The claim that weak open models can collaborate up to commercial level rests on those few runs.
- The authors saw instability when combining models with different capabilities and call for better orchestration strategies. No measurement of it is given.
- Review gains are not monotone. Extra review rounds sometimes lower accuracy ("oscillations"), so more reviewers is not safely better.
- The cost and judge/retriever analyses use at most 500 samples per run because of rate limits and budget, so those curves are noisier than the main tables.
- GPT-3.5-Turbo is not tuned for code, so the authors expect the PAL-based results to be understated.

## What it leaves untried
- It never separates the effect of collaboration from agent count and cost. Compute-matched comparisons are shown only as token plots on a few sets, and the headline comparison gives Corex five agents against ten voting samples.
- It tests no mechanism for the failure it raises itself, an erroneous consensus or a dominant strong model. Discuss ends on agreement and the judge reads both sides, with no check on whether a confident wrong team wins.
- Mixed-model teams are explored only through the judge, the retriever and LLaMA-primary Review. The main results use a single backbone, so the "diversity" argument is mostly untested.
