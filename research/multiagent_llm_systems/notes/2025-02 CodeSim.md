# CodeSim: Multi-Agent Code Generation and Problem Solving through Simulation-Driven Planning and Debugging

## One line
A three-agent pipeline (planning, coding, debugging) that checks both the plan and the code by having the LLM trace sample inputs step by step, and beats the prior multi-agent system MapCoder with fewer calls and tokens on most settings.

## Method
The problem: strong code generators first draft a program, then lean on external debuggers that need many LLM-tool rounds, and their result depends on how good the first draft is. The previous multi-agent system, MapCoder, copies the stages of a developer (recall examples, plan, code, test) but only tests in the last stage, so a bad plan is not caught until code exists, and it costs many calls.

CodeSim keeps three roles and adds one idea: verification by simulation, which is the LLM writing out, line by line, what the plan or code does on a concrete input and comparing it with the expected output.
- Planning Agent: writes one self-generated exemplar problem with solution (a single one, not MapCoder's several), drafts a plan, then simulates the plan on a sample input. A mismatch triggers plan revision before any code is written.
- Coding Agent: turns the plan into code and runs it on the sample inputs and outputs. If all pass, the code is returned.
- Debugging Agent: on failure, gets the problem, plan, code and execution log, and is told to simulate the code on the failing input to locate the bug, then patch it. It needs no extra generated test cases.

Control is a nested loop: up to d debugging attempts, and if all fail, back to the Planning Agent, for at most p cycles. The harness runs the real sample tests; the simulation itself is only a prompt, so the LLM can mis-trace its own code. The reason it should work is that a trace exposes a wrong hypothesis (for example a missed base case) where plain re-prompting would not.

## Evaluated on
- Beats MapCoder on basic benchmarks with every backbone: with GPT-4o the five-benchmark average is 82.7% vs 79.0% (HumanEval 95.1%, MBPP 90.7%); with GPT-4 81.3% vs 78.6%; with ChatGPT 75.1% vs 70.2%.
- Gains are smaller on contest-level problems: with GPT-4, 29.1% on CodeContest (MapCoder 28.5%) and an identical 22.0% on APPS; with ChatGPT 14.2% vs 12.0% average.
- Both simulation parts matter: on HumanEval with GPT-4o, removing both gives 92.1%, either one alone 93.3%, both 95.1%. The gap is 3.2 points, from one benchmark and one model.
- Helps small open models: Gemma2-9B average 75.8% vs 58.7% for direct prompting, LLaMa3.1-70B 80.1% vs 53.4%. MapCoder was excluded there because those models failed its output format, so the comparison to it is untested.
- Cheaper than MapCoder on average: 9.3 vs 15.2 API calls and about 4.13K fewer tokens, with a 7.1% mean accuracy gain. This is not uniform: with GPT-4, tokens rose on MBPP (-0.26K saved) and CodeContest (-2.95K).
- Stacks with an external debugger (LDB) after the first pass: 97.6% on HumanEval with GPT-4o, versus 94.5% for Reflexion plus LDB; Reflexion's second pass used 39K more tokens.
- Extra synthesized tests hurt: self-generated test cases dropped ChatGPT HumanEval from 86% to 78%, while 5 extra human-made sample I/Os raised it to 89%.

## Limitations admitted by the authors
- Still token-heavy: about 13,640 tokens on average against about 560 for direct prompting, roughly 24 times more.
- Needs an external debugger for its best numbers; the authors state their goal is top performance without external tools.
- Weak on dynamic programming: it has trouble building the DP table, and it does not beat MapCoder on introductory and interview-level APPS problems with ChatGPT, or interview-level with GPT-4.
- Depends on how many sample I/Os exist: HumanEval averages only 2.82 per problem, and automatic generation of more is unreliable (the 78% result above).
- Exemplars are generated by the LLM itself rather than retrieved; simulation uses no external tools; only correctness is measured, not time or memory. Generated code should run in a sandbox.

## What it leaves untried
- No check of whether the LLM's simulation is faithful: no comparison of its traces with real execution, so it is unclear how often a wrong trace passes a bad plan or condemns a good one.
- Gains over MapCoder shrink to near zero on the hardest tests (APPS with GPT-4 is 22.0% for both), and the paper does not isolate which problem types simulation cannot help.
- The claimed extension to math reasoning and question answering is listed as future work with no evidence.
