# EvoMAS: Evolutionary Generation of Multi-Agent Systems

## One line
EvoMAS searches for a task-specific multi-agent system by evolving a declarative configuration (agents, prompts, models, tools, topology) with LLM-driven mutation and crossover, scored by an LLM judge.

## Method
The problem: designing a multi-agent system (MAS) by hand is slow and does not transfer across tasks. Automatic generators fall into two camps. Code generators (ADAS, MAS-GPT) are expressive but often produce systems that do not run. Template-bound generators (AutoAgents, EvoAgent, MetaAgent) run reliably but limit what can be expressed.

The paper's idea is to make the MAS a structured configuration rather than code. A configuration holds an acyclic communication graph plus, for each agent, a backbone model, a system prompt and a tool set. A lightweight runtime interprets it. The generator can then only emit valid fields, so syntax and runtime failures should be rare, while topology, prompts, models and tools can all change.

Per task, a meta-model (an LLM) runs a small evolutionary loop:
- **Select**: pick several seed configurations from a pool by task relevance, preferring complementary strengths.
- **Mutate**: read the execution trace, find the main bottleneck, and edit exactly one component type (prompts, models, tools or topology) so each change can be attributed.
- **Crossover**: take the whole topology from one parent and recombine prompts, models and tools from both.
- **Consolidate**: summarise the evolution trace into a memory entry. Up to 3 similar past entries are shown to the meta-model at each step.

Fitness is an LLM-as-judge score (correctness, completeness, reasoning quality) minus a token and latency cost, so no ground truth is needed at search time. The best configuration runs and then joins the pool, so gains accumulate across a sequential stream of queries. The pool is seeded with human-designed cooperative MAS (peer review, debate, majority vote, MetaGPT, ChatDev). Adversarial agents are excluded.

## Evaluated on
- Beats hand-built and generated systems across three backbones. With automatic model assignment it reaches 58.7% on BBEH, 48.9% on WorkBench and 63.8% on SWE-Bench-Verified. The best predefined MAS reaches 46.2% on BBEH and 44.3% on SWE-Bench-Verified. EvoAgent is +10.5 points behind on BBEH and 7.1 points behind on WorkBench.
- Generated systems run: execution rate is 96.8 to 98.9% across benchmarks. MAS-GPT gets 71.5% on BBEH and 1.2% on SWE-Bench-Lite.
- With Claude-4.5-Sonnet it reaches 79.1% on SWE-Bench-Verified, against 78.8% for the top leaderboard entry at the time of writing.
- The gain is structural, not just more compute. At matched budgets on SWE-Bench-Verified, EvoMAS gets 42.7% at 29M tokens. Best-of-10 gets 37.8% at 40M tokens, and a looped single agent gets no gain (33.6%). With Claude-4.5-Sonnet the figures are 79.1% against 71.4% at 31M tokens.
- The judge is a good enough reward. Oracle ground-truth reward adds only 1.5 to 3.4 points. A Qwen3-235B judge agrees with ground truth 90.4% of the time and costs 1.8 points.
- Seeds and depth matter. An empty pool is 15.6 points worse than the default pool. Three evolution steps (49.1% on BBEH-Mini) beat five (47.6%).
- Evolved systems show specialised verifier and decomposer roles and topologies outside the seed families, with about 70% fewer agents.

## Limitations admitted by the authors
- It trades latency and compute for accuracy, so it suits settings where accuracy comes first. The meta-model uses 7.7% of tokens and 10.6% of time, and the pool needs about 300 to 400 queries to stabilise before cost amortises.
- Only cooperative seed configurations were tried. Adversarial agents with conflicting goals are not considered.
- The search depends on good seeds: an empty pool loses 15.6 points.
- Crossover fails when both parents share the same fundamental weakness (appendix).
- The authors name reducing evolution cost as future work.

## What it leaves untried
- No search for non-DAG topologies. The graph is acyclic by definition, so loops and feedback between agents cannot be evolved.
- Comparison with the other search methods (ADAS, EvoAgent) uses sequential cross-query accumulation for EvoMAS and EvoAgent only. The authors' own check shows a per-query-only gain of 40.4% against 36.6% for a single agent, which is smaller than the headline gaps. This is a small, partial control.
- Reward comes from an LLM judge with an oracle gap of up to 3.4 points. The paper does not study judge failure or gaming of the judge by evolved configurations, and does not test tasks where a judge is weak.
