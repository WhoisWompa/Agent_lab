# ALMAS: an Autonomous LLM-based Multi-Agent Software Engineering Framework

## One line
A vision paper for a multi-agent LLM system whose agents mirror agile team roles (sprint planner, developer, peer reviewer) and cover the whole software lifecycle, shown on one worked example.

## Method
The problem: LLM coding tools handle isolated tasks (completion, bug fixing) while only a fraction of developer effort is implementation, and large codebases overflow the context window and dilute attention on long prompts. ALMAS proposes one pipeline of role-aligned agents that fits inside a human agile team.

- **Sprint Agent** plays product manager and scrum master. It sharpens the user task, splits it into sub-tasks with acceptance criteria and story-point estimates (few-shot, from earlier work). The acceptance criteria are reused later for unit tests and review.
- **Supervisor Agent** is the controller. It assigns each sub-task to the most suitable LLM from a pool, weighing specialty, size and cost, and tracks agent actions. This is the cost lever, with routing taken from RouteLLM.
- **Summary Agent** preprocesses the repository into structured natural-language summaries per code unit, kept up to date as code changes. These summaries are the compact stand-in for the codebase.
- **Control Agent** localizes the code relevant to a sub-task by retrieval over those summaries (Meta-RAG, from the authors' earlier paper), so the LLM acts as its own retriever. It is also called on failed tests to find the faulty code.
- **Developer/Code Agent** writes code and unit tests, and checks formatting, compilation and test results.
- **Peer Agent** reviews code for function, vulnerabilities, performance, hallucination and quality, and writes a report for a human.

Control passes between agents in that order. Failed tests send work back through the Control Agent; after several failed automatic recoveries control goes to a human with a summarized action history. Humans can adopt single agents (for example Sprint or Peer) in their own workflow, and the agents plug into Jira and Bitbucket. The claim that this fixes the failure modes seen in multi-agent systems (poor task verification, communication breakdown, misalignment) rests on argument, not measurement.

## Evaluated on
- One demonstration, no benchmark: all agents run on GPT-4o, build a Streamlit stock-options visualization app from a single task, then add a bar chart of average stock prices. The paper reports it "rapidly completed" the task and integrated with Jira and Bitbucket. No time, cost, success rate or quality figure is given.
- Per-agent quality is deferred to the authors' earlier papers (Meta-RAG, story-point estimation, vulnerability assessment, hallucination detection); none of those results are restated here.
- The cost-efficiency claim (summaries cut long-run token use, routing picks cheaper models) is cited from earlier work, with no number in this paper.

## Limitations admitted by the authors
- No end-to-end evaluation: the paper says it "will be explored more thoroughly in future", so the claim that the combined system works is supported only by one example.
- The prototype is partial and uses one model: five agents exist (Summary, Control, Sprint, one Code Agent, Peer), run on GPT-4o only, so the Supervisor's cross-model routing is not exercised in the demonstration.
- The agents were studied one by one, so how errors compound across the chain is unmeasured.

## What it leaves untried
- Running the full system on a benchmark such as SWE-Bench with intermediate metrics like localization efficiency (named as future work). Without it there is no number against single-agent baselines to show that the extra roles help.
- An ablation of the roles: whether Sprint, Peer or Supervisor each change outcomes or cost is not tested, so the case for mirroring agile roles is untested.
- Measuring the failure modes it says it addresses (verification failures, misalignment) with a failure taxonomy or counts.
