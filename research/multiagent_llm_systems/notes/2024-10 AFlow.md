# AFlow: Automating Agentic Workflow Generation

## One line
AFlow searches for a task's whole agentic workflow (prompts plus code-defined control flow) with Monte Carlo Tree Search, using an LLM to propose edits and execution scores to guide it.

## Method
**Problem.** Hand-built workflows cost human effort and do not transfer across tasks. Earlier automation covers only part of the design space. Prompt optimizers (DSPy, TextGrad) need a manually fixed workflow. GPTSwarm's graph representation struggles with conditional logic. ADAS does search over code, but keeps a flat list of past workflows and uses a linear heuristic search. The paper says this makes it inefficient and unable to find effective workflows within a small iteration budget.

**Representation.** A workflow is a set of LLM-calling nodes (model, prompt, temperature, output format) joined by edges written as code. The authors choose code because it expresses sequences, conditions and loops directly. To keep the search tractable they fix model, temperature and format, so only prompts and the code edges vary. They add "operators", reusable node combinations taken from known techniques: Generate, Format, Review and Revise, Ensemble, Test, Programmer, plus a basic Custom node.

**Search.** Each tree node is a complete workflow. One iteration has four steps:
- Selection: with probability mixing uniform choice (weight 0.2) and score-weighted choice (temperature 0.4), pick a past workflow. The initial blank workflow stays in the pool, so the search can always restart and escape local optima.
- Expansion: an LLM optimizer (Claude-3.5-sonnet) makes one modification to the chosen workflow. It sees that workflow's accumulated record of past edits, whether each helped or hurt, and the logged predictions against expected outputs.
- Evaluation: run the candidate on a validation set, five times, and average. The set is filtered to problems whose scores varied across runs of a blank template. Real execution feedback is possible because the tasks have numeric metrics.
- Backpropagation: write the score and the edit's outcome back to the parent's record.

Search stops after 20 rounds, or earlier if the top-k average does not improve. The main claim is that the tree keeps per-workflow experience, which a flat history loses as the prompt grows, so the optimizer is not left to reason from an ever-longer context.

## Evaluated on
- Beats all baselines on six benchmarks with GPT-4o-mini as executor: 80.3 average against 76.0 for the best manual method (self-consistency CoT) and 67.2 for ADAS. The paper reports +5.7% over manual methods and +19.5% over automated ones.
- The gap is largest on hard tasks. On MBPP, AFlow scores 83.4 and ADAS 53.4; on MATH level 5, 56.2 against 35.4. ADAS scores below plain direct prompting (IO) on both: 71.8 and 48.6 respectively.
- Cheaper models can match stronger ones. On HumanEval, an AFlow workflow found with GPT-4o-mini and run on DeepSeek-V2.5 matches GPT-4o direct prompting at 4.55% of its dollar cost. AFlow with GPT-4o-mini beats it at 8.05% of the cost.
- Operators help but are not required. Without them, AFlow still reaches 93.1 on GSM8K, above all manual baselines (best 92.8), and invents ensemble-like structures itself.
- Workflows transfer partly. On HumanEval, most workflows found with one model beat baselines on other models. But the one found with DeepSeek scores 90.8 on GPT-4o-mini, against 94.7 for the one found with GPT-4o-mini itself. The authors conclude each model needs its own workflow.

## Limitations admitted by the authors
- Scope is reasoning tasks with numeric evaluation functions. The loop depends on executable scores, and the paper shows nothing on open-ended tasks.
- Operators are human-designed. They speed the search (the ablation shows faster gains) and so the result is not fully automated.
- The search space is narrowed by fixing model, temperature and output format. Searching these would be a larger space, and the paper does not do it.
- A workflow does not fully transfer between executor models (90.8 against 94.7 above), so the search is repeated per model.
- Evaluation is costly: each candidate runs five times on the validation set. The authors accept this for cleaner feedback.

## What it leaves untried
- Searching over model choice per node. Per-node model assignment is what makes the cost and quality trade-off interesting, but the model is held fixed.
- Tasks without an automatic metric. A learned or judge-based score would be needed there, and its noise would affect the search; the paper does not test this.
- Variants of the search itself, such as different selection settings (0.2 and 0.4 are used). No evidence is given that these values matter.
