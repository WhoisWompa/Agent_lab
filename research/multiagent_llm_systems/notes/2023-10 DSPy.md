# DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines

## One line
A programming model where LM pipelines are written as composed declarative modules and a compiler automatically bootstraps their few-shot demonstrations (or finetunes) against a metric, replacing hand-written prompt templates.

## Method
The problem: LM pipelines (RAG, multi-hop retrieval, agents) are built from long hand-crafted prompt strings found by trial and error. The authors call this brittle, like hand-tuning classifier weights: a prompt does not carry over across pipelines, LMs, domains or even inputs, and the sensitivity compounds when several calls must work together.

The proposal borrows the neural-network abstraction (layers plus optimizers) and has three parts.
- **Signatures**: a short typed declaration of what a call must do, such as `question -> answer`. Field names carry the semantics. The signature says what to do, not how to prompt a given LM.
- **Modules**: Predict, ChainOfThought, ReAct, MultiChainComparison and ProgramOfThought each expand a signature into a prompting technique. They are drop-in replacements for each other. ChainOfThought is a few lines that prepend a "rationale" output field. Modules are parameterized by LM, instructions and, mainly, a list of demonstrations. Pipelines are ordinary Python control flow over modules (define-by-run, as in PyTorch).
- **Teleprompters** (optimizers): given a program, a small training set and a metric, they run in three stages. (1) Candidate generation: run a teacher (or the zero-shot program) on training inputs, keep the multi-step traces whose final output passes the metric, and use every module's input and output in those traces as demonstrations. This is rejection sampling, and it needs labels only for the final output, not intermediate steps. (2) Parameter optimization: choose among candidates by random search or Optuna, or finetune a small LM on them. (3) Higher-order edits: for example, ensembling several compiled copies with a majority vote.

Why it should work: a well-decomposed program usually lets the LM pass the metric on at least a few training examples, and those successes become the teaching signal for every stage. Teleprompters compose, so an expensive teacher program can supervise a cheap one, such as a Llama2-13b ensemble supervising a T5-Large finetune.

## Evaluated on
- Compiling beats hand-written demonstrations. On GSM8K, the ChainOfThought program on GPT-3.5 reaches 72.9 test accuracy with bootstrapping, against 72.4 with human reasoning chains. This supports the claim that expert prompts are not needed.
- Compiling lifts weak programs a lot. GPT-3.5's vanilla `question -> answer` program goes from 25.2 uncompiled to 61.7 with twice-nested bootstrapping. Llama2-13b-chat goes from 9.4 to 36.5.
- Composing modules adds more. The five-chain "reflection" program with an ensemble reaches 86.7 dev for GPT-3.5 and 46.9 test for Llama2-13b-chat. The paper gives no test number for GPT-3.5 here.
- On HotPotQA, a two-hop retrieve-then-answer program gains from bootstrapping. GPT-3.5 test answer EM is 31.2 with few-shot and 39.6 with bootstrap, and 45.6 with an ensemble, scored on half the test set because of cost. Llama2-13b-chat goes from 31.3 to 36.4 to 41.0.
- A small model can stand in for a large one. A compiled T5-Large (770M parameters) gets 39.3 answer EM on dev from 200 labeled and 800 unlabeled questions. Compiling takes minutes to tens of minutes.

## Limitations admitted by the authors
- Scope is narrow. Only two tasks (GSM8K, HotPotQA) are studied, with a handful of programs. Results on other tasks such as information extraction and synthetic data generation are deferred to future work, so generality is asserted from use, not measured.
- Mostly demonstrations are optimized. Instructions and field prefixes are listed as parameters, but the case studies tune demonstrations. Higher-order program changes are limited to ensembling, and the paper lists test-time bootstrapping and backtracking as future work.
- Comparisons with other papers are informal. The authors say evaluation methodology and test samples vary widely across studies. One result is on half the test set, and random few-shot baselines average only 3 to 5 runs.
- Typed field constraints (bool, int) are experimental and not core.
- Evaluation covers only the prompt-engineering question (H1 to H3). Developer effort, code intuitiveness and compute cost are not measured, though the paper names them as other dimensions.

## What it leaves untried
- Optimizing instructions and prompt wording jointly with demonstrations, which would test whether demonstration bootstrapping is the only lever that matters.
- Metrics that are themselves DSPy programs (a faithfulness checker, say). The paper encourages this but does not run it, so the risk of gaming a learned metric stays unexamined.
- Controlled comparisons against the hand-built agent frameworks (LangChain and similar) it criticizes. Only literature numbers are cited, not matched runs.
