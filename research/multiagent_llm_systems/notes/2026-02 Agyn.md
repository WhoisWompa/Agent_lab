# Agyn: A Multi-Agent System for Team-Based Autonomous Software Engineering

## One line
A production-built team of four agents (manager, researcher, engineer, reviewer) resolves GitHub issues through pull requests and review, and reaches 72.2% on SWE-bench 500 without benchmark tuning.

## Method
The problem: most SWE-bench systems use one agent that analyses, edits and validates, or a fixed pipeline with a preset number of stages. The authors argue that this forces very different jobs (wide-context analysis, precise editing, review) into one configuration, and that it drops the review step real teams rely on. Their hypothesis is that organizational structure matters about as much as model quality.

The solution copies a human engineering team on the open-source Agyn platform.
- **Roles.** The manager only coordinates: it holds task state and decides which agent to call next. The researcher explores the repository and writes a task specification. The engineer implements and runs tests. The reviewer opens a GitHub pull-request review with inline comments and either approves or requests changes.
- **Model per role.** The manager and researcher run GPT-5. The engineer and reviewer run GPT-5-Codex, a smaller code-specialised model. The reason given is cost and fit to each stage's needs.
- **Isolation.** Each agent has its own sandbox with a shell and the Nix package manager. The authors found that starting from a minimal environment beat preconfigured ones, because some repositories need downgraded interpreters or libraries. Outputs over 50,000 tokens go to a file instead of into the context.
- **Communication.** Agents never talk to each other. Everything passes through the manager's `manage` tool, which is chosen for traceability and simple control flow. The manager follows a methodology (research, specification, pull request, review until approval) but the number of loops is not fixed.
- **Harness-enforced stopping.** A task counts as done only when the reviewer approves the pull request, not when an agent says it is finished. The manager must end through a `finish` tool, and a plain-text reply triggers an instruction to keep working. Prompts discourage asking for human approval. Context is summarised automatically at a threshold.
- **GitHub tooling.** An MCP GitHub integration returned so much metadata that it hurt performance, so they moved to the `gh` command line plus a custom `gh-pr-review` extension for inline reviews.

## Evaluated on
- Resolves 72.2% of SWE-bench 500 fully automated, the top score among GPT-5-family systems: OpenHands + GPT-5 71.8%, mini-SWE-agent + GPT-5.2 (high reasoning) 71.8%, mini-SWE-agent + GPT-5 (medium) 65.0%.
- That is 7.2 points over the mini-SWE-agent baseline with comparable models by the table. The contributions list says 7.4%, and the paper does not reconcile the two.
- The score is not the highest overall: mini-SWE-agent with Gemini 3 Pro Preview gets 74.2%, and the authors say many systems cluster at 70-75%. They tell readers to treat small gaps with caution.

## Limitations admitted by the authors
- Runs depend on the trajectory. Early environment or dependency failures can derail a run for good. Failed runs were resumed from persisted GitHub artifacts, so the 72.2% is not a clean single-pass number.
- Old repositories have broken CI and legacy dependencies. Agents spent context and time fixing them, so the authors told agents to ignore unrelated CI checks, which is a benchmark-specific instruction despite the "not tuned" claim.
- Agents over-engineer, adding tests or refactors, so correct patches sometimes differ from the minimal gold patch.
- Slow test suites hit tool time limits, and the workarounds the agents tried changed their trajectories.
- Early on, the manager waited on agents that had already finished, which stalled runs. It was fixed by requiring explicit completion signals.
- The evaluation ran on one MacBook Pro and hit out-of-memory failures when too many tasks ran in parallel.

## What it leaves untried
- No ablation: nothing removes the reviewer, the manager, or the split between models. The claim that team structure drives the gain over a single agent is therefore unsupported, since the one baseline gap (65.0%) also differs in scaffold and model setting.
- No cost, token or time figures, although cost efficiency is the stated reason for role-specific models.
- The manager-only communication was chosen by design. Direct agent-to-agent links, which the platform supports, are not compared.
