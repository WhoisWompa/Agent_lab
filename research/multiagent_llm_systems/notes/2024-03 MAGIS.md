# MAGIS: LLM-Based Multi-Agent Framework for GitHub Issue Resolution

## One line
Four role agents (Manager, Repository Custodian, Developer, QA Engineer) split a GitHub issue into per-file tasks, locate the lines to edit, and review each patch, lifting GPT-4's SWE-bench resolved rate from 1.74% to 13.94%.

## Method
The problem: a bare LLM resolves under 2% of SWE-bench issues. The authors' empirical study of why finds three factors. (1) More retrieved files raise recall but can lower the resolved rate: for Claude-2 recall rose from 29.58 to 51.06 while the resolved ratio fell from 1.96 to 1.22. (2) Locating the right lines matters: line-coverage ratio is positively associated with resolution (coefficient 0.5997, significant only for Claude-2; the GPT models had too few successes to test). (3) Complexity hurts: the number of files and functions in the reference change is negatively correlated with resolution for all three LLMs.

MAGIS answers each factor with a role.
- **Repository Custodian** ranks files by BM25 against the issue, keeps the top k, then filters them with an LLM relevance check. To avoid re-reading long files on every commit, it keeps a memory of file summaries. A new file version is described as the old summary plus an LLM-written "commit message" for the git diff, which saves context and cost.
- **Manager** turns the issue into one task per surviving file and writes a role description for a Developer agent per task, so the team is built to fit the issue instead of being fixed in advance. A kick-off meeting (round-robin speech, Manager opens and summarises) checks that the tasks fit together and which are independent or ordered. The resulting plan is emitted as code and executed.
- **Developer** first names the line ranges to change, then regenerates only those ranges. This splits "edit existing code" into locate, then generate, then diff.
- **QA Engineer**, paired with each Developer, reviews the diff and returns a comment and an accept/reject decision. The loop repeats until acceptance or an iteration cap.

The harness (git diff, patch application, the executed plan) does the mechanical work. The LLM handles judgment: relevance, task definition, review.

## Evaluated on
- Beats every baseline on a 25% SWE-bench subset: 13.94% resolved vs 1.74% for GPT-4, 4.88% for Claude-2, 4.36% for SWE-Llama 13b. Applied ratio is 97.39%, versus 13.24% for GPT-4.
- QA review helps: removing it drops 13.94 to 10.63 (with hints) and 10.28 to 8.71 (without hints).
- Hints (human comments from the pull request, available before the first commit) add 3.66 points with QA: 13.94 vs 10.28. Without hints and QA the system still reaches 8.71%, five times GPT-4.
- The Custodian's recall beats plain BM25 at each file count (plot only; no numbers given in the text).
- Developer line coverage is closer to 1 than the baselines' (plot only). Complexity correlations shrink for MAGIS: the file and function coefficient is -1.55, against -25.15 for GPT-4.
- On SWE-bench Lite, 25.33% vs 16.11% (mean of 3 runs) for AutoCodeRover, with 22.33% for its union of 3 runs, and 18.00% for SWE-Agent. On 140 shared instances against Devin it resolves 21 (15%) vs 18 (12.86%), and the authors call this comparison not equitable.

## Limitations admitted by the authors
- Prompt design affects results, and the authors say prompt bias cannot be fully removed. No prompt sensitivity test is reported, so how much of the gain comes from wording is unknown.
- Only 12 Python repositories are tested, and the authors note that microservice and functional-programming styles are missing. Generality beyond them is unvalidated.
- The comparison with Devin is not like for like: different instance sets (140 shared), unknown underlying LLM, and Devin used tools and the full repository.
- Resolved patches contain more added lines than human fixes, mostly comments. Unresolved patches tend to delete more lines; the authors name this room for improvement.

## What it leaves untried
- The best score uses human PR hints. The text does not say whether a deployed system would have them at issue time, so the 13.94% figure may not be reachable without them (8.71% to 10.28% without).
- Only GPT-4 is used as the base model, so it is not shown whether the roles help weaker or stronger models. Role-by-role ablation is limited to QA and hints, not the Manager's meeting or the Custodian's memory.
- QA is the same LLM reviewing its own team's patch without running tests. Adding test execution to the review loop is not tried.
