# CAMEL: Communicative Agents for "Mind" Exploration of Large Language Model Society

## One line
Two chat LLMs, one playing an instructing "user" role and one an executing "assistant" role, cooperate on a task from a one-line human idea, steered only by an opening set of prompts ("inception prompting").

## Method
Problem: chat models need a human to write every prompt and steer every turn, which is costly and needs domain expertise the user may lack. CAMEL replaces the human with a second agent.

- A human supplies a rough idea and two roles (for example "trading bot", Python Programmer, Stock Trader). A task-specifier agent turns the idea into a concrete task.
- The AI user is the planner: it issues one instruction at a time (with an optional input). The AI assistant is the executor: it answers each with a solution and ends with "Next request". Each sees the full conversation so far.
- Prompting happens only once, at the start (task specifier prompt plus two nearly symmetric system prompts). After that the two agents prompt each other in a loop. This is the "inception" idea.
- The prompts carry the control. They forbid role flipping ("Never flip roles! Never instruct me!"), force a fixed reply format against vague "I will..." replies, and give the user a single end token, `<CAMEL_TASK_DONE>`, to stop the chat.
- The harness backs the prompts with hard stops: end if the user gives no instruction for 3 rounds, end if the assistant instructs (a role flip), end on the token or token limit, and cap at 40 messages because cost grows quadratically with length.
- An optional critic agent (AI or human) picks among proposals or gives feedback, for tree-search-like control. It is only sketched in the appendix and not evaluated in the main text.
- The same loop is used at scale to generate instruction-following conversation data (AI Society, Code, plus single-turn Math and Science sets), which the authors then use to fine-tune LLaMA-7B.

Observed failure modes without these guards: role flipping, the assistant repeating the instruction, flake replies, and infinite thank-you/goodbye loops. Sometimes the agents notice the loop and still cannot leave it.

## Evaluated on
- Multi-agent solutions beat a single gpt-3.5-turbo answer: on 100 AI Society tasks, humans preferred CAMEL 76.3% vs 10.4% (13.3% draws); GPT-4 as judge agreed, 73.0% vs 23.0%. On 100 Code tasks GPT-4 judged 76.0% vs 24.0%. Solutions were first summarised by GPT-4 so the format does not give them away.
- Fine-tuning LLaMA-7B on the generated data adds domain knowledge: each added dataset improves answers on its own domain in GPT-4 comparisons (for example Science 47 wins of 60 after adding the Science set, against 13 losses).
- The fully fine-tuned CAMEL-7B scores HumanEval pass@1 14.0 vs 10.5 for LLaMA-7B and 11.0 for Vicuna-7B; pass@100 is 57.9 vs 36.5 and 42.9. It remains far below gpt-3.5-turbo (69.4 pass@1).
- The four failure modes are shown by examples only. No rate of how often each occurs, or how much each guard reduces it, is reported.

## Limitations admitted by the authors
- Evaluating task completion across so many diverse tasks would need many domain experts, so quality is judged by humans and GPT-4, which may be biased. Human raters may favour longer answers, which are not always better.
- The generated data and the fine-tuned model can contain false information, because the LLMs hallucinate.
- Weakly aligned LLMs are easily exploited: the authors show a malicious-role example where the agents plot to "take control of the world".
- Cost of the OpenAI API limited the work; the authors say it "only touches the tip of the iceberg".

## What it leaves untried
- More than two agents and competing agents. The formulation is said to extend through message-passing graphs, but only the cooperative two-agent case is run.
- Measuring the termination and role-flip guards, so that one could tell which prompt line or hard stop does the work.
- Checking solution correctness by execution (the Code comparison relies on GPT-4 opinion, and human review was skipped for code because code is hard to judge without running it).
