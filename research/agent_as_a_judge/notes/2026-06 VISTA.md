# VISTA: A Versatile Interactive User Simulation Toolkit for Agent Evaluation

## One line
A user-simulation toolkit that tests customer-facing agents with a simulated user who can both click through the real web UI and call user-side APIs, plus six metrics that score how realistic and how thorough the simulated conversations were.

## Method
Two gaps in simulation-based agent evaluation: nobody measures whether the simulator actually exercised the agent (prior metrics check human-likeness or task checkpoints), and simulators are either UI-only (expensive, error-prone on noisy raw DOM) or API-only (cheap, but limited to its tool list).

The hybrid simulator runs an observe-plan-act loop. A scenario (user profile, goal, domain knowledge) becomes the simulator's system prompt. At each step an LLM router decides whether to call a user-side API first. These are general tools (web search, preference memory) and task-specific mocked APIs built from the real database schema that return structured status and realistic errors, sampling failure outcomes at random (e.g. "reschedule button is missing"). The router is told to "prefer API actions when in doubt". The tool result feeds UXAgent's web connector, which outputs one UI action (click, type into the chat widget, scroll). The bet: APIs give precise facts, the UI keeps full user freedom.

The metrics (the more reusable idea):
- **Coverage**, computed from the *product agent's* tool calls. Transition entropy is the normalized Shannon entropy of each row of the next-tool transition matrix, averaged over non-empty rows (are routes varied?). Tool-distribution entropy is the normalized entropy of overall tool frequencies (are all tools used?). Trajectory distance is the mean pairwise normalized Levenshtein distance between (tool, arguments) sequences within one user goal (do repeated runs of the same goal differ?).
- **Realism**: an LLM judge returns true/false on whether user turns match the given profile, goal and knowledge.
- **Cost**: tokens and actions per turn.
- **Failures found**: an LLM scores each agent reply on five dimensions (0-4), and a second LLM merges the justifications into a count of unique failures.

The assumption that carries everything: wider tool-call diversity means more of the agent's failure surface gets probed.

## Evaluated on
- Hybrid finds more unique failures: 79 vs 69 (UI-only) vs 64 (API-only) on the Shopify agent with gpt-5.4; 34 vs 24 vs 30 on education (the paper's "up to 42% more").
- The coverage gains are small: transition entropy 0.34 vs 0.33 and trajectory distance 0.96 vs 0.94 (shopping, gpt-5.4). The paper's "up to 12%" is the largest relative gap.
- Cost: hybrid tokens per turn are close to UI-only (69.1k vs 79.9k) but more than 100x API-only (0.5k).
- Human Likert ratings (1-3) favour hybrid slightly: human-likeness 2.04 vs 1.97 vs 1.92 (shopping), SDs 0.34-0.66. In the human-vs-bot test, hybrid was mistaken for a human 6.3% more often than UI-only and 18.7% more often than API-only.
- "Higher coverage goes with more failures" rests on hybrid scoring equal or higher in all 12 rows; no correlation coefficient.

## Limitations admitted by the authors
- LLM simulators do not faithfully model humans; cited work shows they are overly cooperative and surface different failures than real users, and the hybrid inherits this.
- Only two domains, so generality is untested.
- The metrics measure coverage and interaction quality, not real deployment success. No link to downstream outcomes is shown.
- UI/API routing needs environment-specific integration, so setup is heavier than single-mode simulators.

## What it leaves untried
- Validating "unique failures" against humans. The count comes from two chained LLM judges, never checked for false or duplicate failures, so "42% more" could partly be judge noise. Annotator agreement on realism was only moderate (Cohen's kappa 0.45).
- Separating simulator diversity from task variety and chance. The coverage metrics are computed on the product agent's tool calls, and the mocked APIs sample random failure outcomes, so higher entropy may come from the injected randomness and not from better user behaviour. Fixing tool outcomes would test this.
- Significance testing. Coverage differences of 0.01-0.03 and Likert gaps far smaller than the standard deviations are reported as consistent wins with no test, and the conclusion's claim that the metrics "align closely with human judgments" comes with no correlation statistic.
